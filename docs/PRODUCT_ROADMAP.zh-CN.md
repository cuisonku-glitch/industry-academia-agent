# 双端产学研转化平台：产品设计与开发路线图

> 文档状态：讨论稿 v1；当前版本：`v0.1.2`；更新日期：2026-09-01。目标：把现有“企业需求—教师/论文匹配原型”升级为可追溯的企业方案生成、院校成果分析与论文关系版图平台。

按依赖关系拆分的实际施工顺序与验收闸门见：[后续完整实施顺序](IMPLEMENTATION_SEQUENCE.zh-CN.md)。

## 1. 结论先行

产品建议分为三个一级入口：

1. **企业端·组合方案**：从企业需求原话出发，完成需求确认、技术问题拆解、组合方案、技术路线、论文/教师匹配、转化评估和落地计划。这是下一阶段的最高优先级，也是产品的核心价值。
2. **院校端·成果对接**：围绕论文库提供上传、检索、精读总结、技术路线提取、产业转化分析、报告预览和下载。
3. **谱系版图**：用可解释的论文关系图展示论文、教师、技术、材料和应用场景之间的远近与演化关系。

当前版本已经具备可追溯需求解析、论文向量检索、教师画像、透明匹配评分、证据审查、Kimi RAG 和 Markdown 报告底座，但还没有真正完成“组合方案—技术路线—转化评估—落地方案”闭环。因此开发顺序应当是：

**先规范数据与证据 → 做企业端闭环 → 做院校端工作台 → 做谱系版图 → 再做多用户和公网部署。**

截图中的三栏工作台结构可以采用，但截图中的“2921 篇”等数字只作为界面构想，不代表当前项目的真实数据规模。所有数量必须由本地论文库实时统计，不能写死。

## 2. 产品定位与边界

### 2.1 产品要解决的问题

企业通常只有业务语言和目标，院校通常只有论文、成果和研究方向。两者之间缺少一层可验证的“工程翻译”：

- 企业问题怎样拆成可研究、可测试的技术模块；
- 哪些论文能支撑哪个模块，而不是只给出“相似论文”；
- 多篇论文或多位教师的能力怎样组合成一条技术路线；
- 从论文结果到企业现场还缺哪些验证、设备、工艺、成本和合规条件；
- 什么时候应该继续，什么时候应该暂停或补证据。

这个平台的核心不是替企业“自动拍板”，而是产出一份**证据可定位、假设可区分、评分可复算、缺口可暴露、方案可人工修改**的决策草案。

### 2.2 明确不做的承诺

- 不把语义相似度包装成“产业化成功率”。
- 不因论文写过某项性能，就宣称已经可以规模化生产。
- 不把 Kimi 的推断写成论文事实。
- 不在没有专利、法规、成本和现场验证数据时给出确定性结论。
- 不把二维谱系图上的视觉距离解释为唯一、客观的学术关系。
- 不对每篇论文重新训练 Kimi；系统继续采用本地检索增强生成（RAG）。

## 3. 总体信息架构

### 3.1 顶部一级导航

| 页面 | 主要用户 | 核心任务 | 优先级 |
| --- | --- | --- | --- |
| 企业端·组合方案 | 企业技术负责人、项目经理、转化人员 | 把真实需求变成证据化组合方案与落地计划 | P1，最高 |
| 院校端·成果对接 | 导师、科研管理人员、成果转化人员 | 管理论文、生成精读与转化分析 | P2 |
| 谱系版图 | 双方用户 | 查看成果关系、技术演化和方案证据子图 | P3 |

三个页面共享同一份论文库、教师画像、证据记录和报告模型，避免各页面各自生成一套互相矛盾的数据。

### 3.2 页面布局原则

院校端采用截图中的三栏桌面工作台：

- **左栏：论文来源库**——上传、索引状态、教师/论文模糊搜索、筛选与选中论文；
- **中栏：分析工作台**——精读总结、技术路线、转化分析、完整评估；
- **右栏：报告预览**——章节导航、引用跳转、Markdown/PDF 下载。

企业端也采用相同交互语言：

- **左栏：需求与项目记录**——需求原话、历史版本、待确认问题；
- **中栏：方案工作台**——需求拆解、候选方案、技术路线、转化评估；
- **右栏：证据与报告预览**——论文页码证据、假设、风险、报告下载。

谱系版图适合使用接近全宽的画布，左侧或顶部保留搜索、关系类型、年份、教师和最小关系强度等筛选器。

在 Streamlit 中建议用 `st.navigation` 和 `st.Page` 建立三个真正的页面，而不是继续把所有重任务放在同一个标签页中。复杂分析使用提交式表单；模型和向量库作为共享缓存资源；长任务先显示稳定页面与进度状态，避免每次点击都重新加载模型。

## 4. 企业端：核心方案闭环

企业端是本项目下一阶段的主线。建议把它实现为七个有状态、可回退的步骤，而不是一次大模型调用直接生成长报告。

### 4.1 第一步：接收需求原话并建立证据映射

输入可以是文本，后续再扩展为需求文档。结构化字段至少包括：

| 字段 | 示例含义 | 规则 |
| --- | --- | --- |
| 行业/场景 | 产品实际使用环境 | 必须映射到企业原话，未知则标“待确认” |
| 产品/系统 | 企业正在开发或改造的对象 | 保留原始措辞 |
| 现存问题 | 当前性能、成本、制造或交付痛点 | 不把“期望”误当成“现存故障” |
| 目标指标 | 数值、单位、测试条件、目标区间 | 没有数值时主动列为澄清项 |
| 约束条件 | 成本、周期、尺寸、设备、材料、法规等 | 区分硬约束与偏好 |
| 已有基础 | 已有样机、工艺、设备、数据、团队 | 用于判断起始成熟度 |
| 排除方案 | 企业明确不能采用的路线 | 防止方案生成偏离边界 |
| 原文证据 | 字段对应的原文片段或位置 | 所有抽取字段必须可回溯 |

当前规则解析器可以继续承担高确定性的基础识别，但要补一个“人工确认页”。不确定项不能自动补全，应显示：

- 已从原文确认；
- 系统推断，等待确认；
- 信息缺失，需要企业补充。

### 4.2 第二步：把需求拆成技术问题树

需求拆解不应只有关键词，而应形成以下层级：

**业务目标 → 产品问题 → 技术子问题 → 所需能力 → 可验收指标 → 约束与依赖**

每个技术模块应保存：

- 模块编号与名称；
- 对应的企业原文；
- 要解决的技术问题；
- 输入、输出和接口；
- 目标指标及测试条件；
- 已知约束；
- 前置依赖；
- 缺失信息；
- 人工确认状态。

这样做的关键价值是：后面的论文检索针对每个模块分别进行，而不是拿整段企业需求做一次宽泛检索。

### 4.3 第三步：按模块检索论文和教师证据

每个技术模块生成独立检索式，并结合以下检索方式：

- 本地向量语义检索；
- 教师、作者、论文题名、年份等元数据过滤；
- 技术、材料、器件、工艺和应用实体匹配；
- 后续可选的引用关系与关键词检索。

每条证据必须携带：论文、作者/导师、页码、Chunk、原文摘录、检索相似度以及它支撑的具体模块。系统要允许用户查看“为什么匹配”，也要显示没有足够证据的模块。

### 4.4 第四步：生成两个或三个候选组合方案

Kimi 的职责是基于已确认需求和已检索证据组织候选方案，不是凭空发明技术事实。每个候选方案至少包含：

- 总体原理与适用边界；
- 由哪些技术模块组成；
- 每个模块匹配哪篇论文、哪位教师、哪段证据；
- 多篇论文或多位教师之间怎样衔接；
- 可预期价值；
- 需要补充验证的假设；
- 当前无法覆盖的技术缺口；
- 为什么它与其他候选方案不同。

建议至少形成三个方案方向：

- **低风险方案**：优先复用证据充分、成熟度较高的技术；
- **均衡方案**：在性能、成本和周期之间折中；
- **探索方案**：潜在收益更高，但验证缺口和不确定性更大。

这些名称是方案策略模板，不是对企业真实数据的预判。若证据不足，允许只输出一个方案或明确输出“暂不能形成可靠方案”。

### 4.5 第五步：形成可执行的技术路线

技术路线应是有依赖关系的节点图，而不只是几段描述。建议节点结构为：

- 节点名称和阶段；
- 输入；
- 关键动作或实验；
- 输出物；
- 验收指标和测试方法；
- 前置节点；
- 预计责任方；
- 风险与替代路线；
- 论文或需求证据；
- 当前状态。

典型阶段可以包括：需求规格确认、实验室可行性验证、关键模块验证、集成样机、中试/放大、现场验证、成果转移。具体阶段必须由项目情况决定，不能机械套用。

技术路线先保存为结构化“节点 + 边”数据，再生成三类产物：

1. 网页中的可视化预览；
2. 可下载的 PNG/SVG；
3. 可继续编辑的 `.drawio` 文件。

已经安装的 draw.io 能力可以辅助开发阶段生成和检查图，但网页运行时不能直接调用 Codex 的 draw.io 插件。因此需要在项目中实现独立的图数据转换与导出器。第一版以流程图预览和 `.drawio` 下载为主；浏览器内直接编辑可放到后续版本。

### 4.6 第六步：进行转化评估

必须把两种评分分开：

- **匹配分**回答“企业需求和教师/论文是否相关”；
- **转化就绪度**回答“这条方案距离工程落地还有多远”。

当前已有匹配分不能直接复用为转化就绪度。转化评估建议先检查硬门槛，再计算透明的维度分。

#### 硬门槛

出现以下情况时，报告应显示“暂停/补证据”，而不是只给一个低分：

- 企业关键指标或测试条件未确认；
- 核心技术模块没有论文或实验数据支撑；
- 关键性能只能由模型推断；
- 必要的安全、法规或知识产权检查尚未进行；
- 方案依赖的设备、材料或人员完全不可获得。

#### 建议的初始评分维度

| 维度 | 初始权重 | 主要依据 |
| --- | ---: | --- |
| 需求契合度 | 15 | 模块覆盖、指标与约束符合程度 |
| 科研证据强度与可复现性 | 15 | 实验方法、样本、对照、页码证据、重复性 |
| 技术成熟度（TRL） | 15 | 原理、样件、实验室系统、现场验证阶段 |
| 工程化与制造成熟度 | 15 | 工艺窗口、面积/产能、良率、设备、质量控制 |
| 性能验证缺口 | 10 | 企业工况下尚未验证的指标 |
| 成本与经济性 | 10 | 材料、设备、制造、维护和替代方案成本 |
| 知识产权、法规与安全 | 10 | 专利自由实施、许可、EHS、行业准入 |
| 团队、资源与进度 | 10 | 人员、平台、供应链、周期和协作基础 |
| **合计** | **100** | 权重应可配置并保留版本 |

同时单独输出**证据完整度/置信度**。未知不等于差：缺少成本数据时，应标“成本未知、置信度下降”，而不是擅自给低成本或高成本结论。

每个维度都要显示：分数、计算规则、证据、缺失项、结论来源类型。来源类型至少分为：

- 企业已确认事实；
- 论文直接证据；
- 系统推断；
- 专家判断；
- 未知。

专利自由实施和法规结论需要专业检索或人工复核，论文库本身不能替代正式法律或合规意见。

### 4.7 第七步：输出落地方案和决策报告

落地方案不是泛泛的“建议合作”，而是阶段化执行表。每个里程碑至少包含：

- 目标；
- 责任方；
- 输入与交付物；
- 验收/退出标准；
- 前置依赖；
- 预算或资源范围；
- 风险与缓解措施；
- 是否进入下一阶段的决策门。

最终报告建议包含：

1. 企业需求原文与确认记录；
2. 结构化需求和问题树；
3. 候选组合方案对比；
4. 推荐方案及推荐理由；
5. 技术路线图；
6. 模块—教师—论文证据矩阵；
7. 转化就绪度与证据完整度；
8. 技术、工程、成本、知识产权和合规缺口；
9. 分阶段落地计划；
10. 引用与审计记录。

## 5. 企业端 Agent 调整建议

现有六 Agent 可以作为底座，但需要从“匹配流水线”扩展为“带人工检查点的决策工作流”。建议角色如下：

| Agent/服务 | 职责 | 是否可直接复用 |
| --- | --- | --- |
| Requirement Agent | 保留原文、抽取确定字段和证据映射 | 扩展现有 |
| Clarification Agent | 生成缺失问题并接收企业确认 | 新增 |
| Problem Decomposition Agent | 建立技术问题树和模块验收指标 | 新增 |
| Research/Paper Agent | 按技术模块检索教师和论文 | 扩展现有 |
| Solution Architect Agent | 基于模块证据生成候选组合方案 | 新增 |
| Route Planner Agent | 形成带依赖与验收标准的技术路线图 | 新增 |
| Transfer Evaluator Agent | 计算转化就绪度和证据完整度 | 新增 |
| Evidence Agent | 检查每项结论是否有来源、是否越界 | 扩展现有 |
| Report Agent | 从统一结构生成 MD/PDF 报告 | 扩展现有 |

Coordinator 需要支持暂停、人工确认、继续、失败重试和版本保存，不能再假设所有 Agent 必须一次连续跑完。

## 6. 院校端：论文成果工作台

### 6.1 论文来源库

左侧论文库统一管理两类来源：

- 项目本地论文目录中已有的 PDF；
- 用户通过网页上传的新 PDF。

上传流程应为：

**选择文件 → 类型/大小检查 → SHA-256 去重 → 保存到隔离目录 → 元数据识别/人工补录 → 文本解析 → 切块 → Embedding → 能力抽取 → 入库完成。**

文件扩展名检查只是第一层防护，不能把 `.pdf` 后缀当成安全保证。应限制单文件大小、拒绝加密或损坏文件、避免覆盖同名文件，并保留导入状态和错误信息。

论文元数据至少包括：题名、作者、导师、院校/学院、年份、关键词、来源类型、文件哈希、页数、导入状态和授权说明。第一版已将三篇论文信息迁移到可审查的种子配置和本地 SQLite 目录；院校/学院、关键词、状态恢复和网页编辑仍需继续补齐。

### 6.2 检索与浏览

第一版支持：

- 导师姓名精确或包含搜索；
- 论文题名模糊搜索；
- 作者、年份、关键词和处理状态筛选；
- 按导师展开论文列表；
- 选中论文后在中栏启用分析功能。

当论文规模达到数千篇时，列表必须分页或虚拟化，不能一次渲染全部论文。搜索结果应由数据库查询返回，页面只显示当前结果。

### 6.3 论文精读总结

精读报告不只生成摘要，建议按固定结构输出：

- 研究问题和背景；
- 核心方法/原理；
- 材料、器件、工艺与设备；
- 实验设计与评价指标；
- 关键结果及对应页码；
- 图表、公式或关键数据说明；
- 创新点；
- 局限性与未验证事项；
- 可复现条件；
- 可产业化方向；
- 与其他论文的关系。

所有事实陈述应尽量指向论文页码或图表。扫描 PDF、复杂表格和论文图片需要独立的 OCR/视觉处理流程，不能假设当前文本解析已经覆盖。

### 6.4 框图和技术路线总结

从论文抽取以下图结构：

- 研究输入或材料；
- 样品/器件制备步骤；
- 表征或实验环节；
- 数据处理；
- 输出结果；
- 决策或对比分支；
- 关键参数与证据页码。

抽取后先在网页展示可审核的节点表和连线关系，用户确认后再生成 draw.io 图。这样可以避免模型把论文中的叙述顺序误画成真实工艺依赖。

### 6.5 转化分析

单篇论文的转化分析与企业端不同，重点回答：

- 论文成果可能服务哪些行业或产品；
- 从实验室样品到可交付成果还缺哪些工程环节；
- 哪些指标已经有直接证据，哪些只是潜力；
- 需要哪些平台、设备、合作团队和测试场景；
- 可以形成技术许可、联合开发、委托测试、样机合作还是其他模式；
- 下一步最小验证实验是什么。

## 7. 报告预览与下载

报告应使用一份规范化的结构化数据作为唯一真源，再由同一份数据生成 Markdown 和 PDF：

**分析结果 JSON → 报告模型 → Markdown → HTML/PDF**

不能分别让模型生成 MD 和 PDF 内容，否则两个版本容易不一致。

第一版建议：

- 右栏立即预览 Markdown；
- 提供 `.md` 下载；
- PDF 生成完成后提供在线预览和 `.pdf` 下载；
- 报告中的路线图作为内嵌图片，同时附 `.drawio` 源文件下载；
- 文件名包含报告类型、论文/项目标识和生成时间；
- 报告保存到独立输出目录，并保留生成参数、模型版本和引用记录。

当前安装的 Streamlit 版本支持文件上传和下载；PDF 在线查看还需要项目增加 PDF 查看依赖。PDF 生成器必须嵌入可用的中文字体，并在 Windows 上进行版式验证。

## 8. 谱系版图：论文关系远近可视化

### 8.1 是否可行

可行，但应称为“可解释的论文关系版图”，而不是把模型降维图当成绝对学术谱系。建议同时提供四种视图：

1. **关系网络**：查看论文、教师、技术、材料和应用之间的连接；
2. **主题聚类**：查看研究方向的簇和相邻主题；
3. **时间演化**：查看某一技术路线随年份的变化；
4. **方案证据子图**：只显示某个企业方案所依赖的论文、教师和技术模块。

### 8.2 节点类型

- 论文；
- 教师；
- 作者/学生；
- 技术方法；
- 材料；
- 器件/设备；
- 应用行业；
- 企业需求模块。

### 8.3 关系类型

- 引用或被引用；
- 同一导师/团队；
- 共同作者；
- 语义相似；
- 使用相同材料、工艺或设备；
- 面向相同应用；
- 明确的技术改进、继承或对比关系；
- 被同一企业组合方案采用。

“关系强度”不能只用一个黑盒相似度。初始可以采用透明组合：语义相似 40%、共同技术/材料/应用实体 25%、引用或明确继承 20%、作者/团队关系 10%、时间连续性 5%。该权重只是起始方案，必须可配置、可复算，并在点击边时解释贡献来源。

二维布局中的距离只用于帮助浏览。用户点击任意连线时，应看到“为什么相连”：共享了什么技术、引用了哪篇论文、相似度是多少、证据来自哪些页。

### 8.4 规模与性能

若论文规模达到数千篇，不能默认把所有节点一次画到浏览器。应采用：

- 搜索后聚焦一个教师、论文或主题；
- 只加载一到两层邻居；
- 最小关系强度过滤；
- 每个节点只保留 Top-K 关系；
- 主题聚合与按需展开；
- 服务端计算、前端增量加载。

第一版可以用 NetworkX 计算关系、Graphviz 或轻量组件展示邻域图。需要缩放、拖拽、节点选择、增量加载和大规模聚类时，再开发 Streamlit Custom Components v2 专用组件；不采用旧版组件接口。

## 9. 数据模型与技术架构

### 9.1 核心实体

| 实体 | 关键内容 |
| --- | --- |
| Paper | 文件、题名、作者、导师、年份、哈希、状态、授权说明 |
| PaperChunk | 文本、页码、Embedding、论文外键 |
| EvidenceClaim | 结论、原文证据、页码、来源类型、置信状态 |
| Person/TeacherProfile | 人员、研究方向、能力、论文来源 |
| EnterpriseNeed | 原文、结构化字段、确认记录、版本 |
| NeedModule | 问题、能力、指标、约束、依赖 |
| SolutionOption | 方案策略、模块组合、假设和缺口 |
| RouteNode/RouteEdge | 技术路线节点、依赖和验收标准 |
| TransferAssessment | 维度分、硬门槛、证据完整度、版本 |
| Report | 结构化结果、MD/PDF 路径、生成记录 |
| GraphEdge | 关系类型、强度、分项贡献和证据 |
| IngestionJob | 上传、解析、切块、入库的任务状态 |

### 9.2 存储建议

- **第一阶段**：SQLite 保存论文元数据、任务、需求、方案和报告索引；
- **继续保留**：ChromaDB 保存论文 Chunk 和向量；
- **文件存储**：本地受控目录保存授权 PDF、图像与报告；
- **谱系关系**：先在 SQLite 中保存边表，NetworkX 按需计算子图；
- **后续扩展**：只有当多用户、并发和图查询成为瓶颈时，再评估 PostgreSQL、对象存储和专用图数据库。

不建议第一版直接上 Neo4j 或拆成很多微服务。当前本地单机项目先把数据契约、证据追溯和业务闭环做正确更重要。

### 9.3 建议的代码边界

```text
app/app.py                         多页面入口和共享资源
app/app_pages/enterprise.py        企业端 UI
app/app_pages/college.py           院校端 UI
app/app_pages/lineage.py           谱系版图 UI
src/library/                       论文库、元数据、上传与索引任务
src/solution/                      问题拆解、候选方案和技术路线
src/evaluation/                    转化评估与证据完整度
src/visualization/                 路线图和谱系图数据/导出
src/reporting/                     统一报告模型、MD/PDF 渲染
src/repository/                    SQLite 数据访问
```

页面文件只负责交互和展示，复杂业务逻辑放在 `src/` 中并用离线测试覆盖。

## 10. 开发优先级

### P0：数据与证据地基

这是后面所有页面共用的基础。

- 设计并固化 Paper、EvidenceClaim、EnterpriseNeed、NeedModule、SolutionOption、RouteNode 和 Report 数据契约；
- 扩展现有 SQLite 论文表，补齐院校/学院、关键词、任务恢复与迁移；
- 建立统一论文库服务、哈希去重、状态管理和失败恢复；
- 规定“事实、推断、专家判断、未知”的标记方式；
- 报告以结构化结果为唯一真源；
- 保留 API 发送同意记录与证据审计轨迹。

**完成标准**：新增论文无需修改 Python 源码；任何结论都能定位来源或明确标为推断/未知。

### P1：企业端组合方案闭环（最高优先级）

- 需求确认与澄清；
- 技术问题树和模块验收指标；
- 模块级论文/教师检索；
- 一到三个有证据差异的候选方案；证据不足时不凑数；
- 技术路线节点图；
- 转化就绪度、证据完整度和硬门槛；
- 阶段化落地计划；
- MD 报告与路线图下载。

**完成标准**：输入一条真实企业需求后，用户能够确认拆解结果，并得到至少一个有模块级论文页码证据、技术缺口、验收标准和决策门的方案；证据不足时系统能够拒绝给出伪确定结论。

**当前状态（2026-09-02）**：P1 纵切已达到上述完成标准。已实现系统解析、网页逐字段修改、追加式本地版本保存与历史恢复、确认冻结、模块级本地检索、证据数量闸门、结构化技术路线、已知项四维转化评估、五项硬门槛、阶段落地计划、Markdown 与原生 `.drawio` 下载。带来源的江西电缆公开榜单摘要已完成本地 CUDA 验收。后续重点是指标本体与单位归一、更多案例和人工金标准评分校准，而不是继续扩充未经校准的假精确分数。

### P2：院校端论文工作台

- 三栏布局；
- 多 PDF 上传、索引状态和错误提示；
- 导师/题名模糊搜索和筛选；
- 论文精读总结；
- 论文技术路线与 draw.io 导出；
- 产业转化分析；
- Markdown 预览与下载。

**完成标准**：一篇新论文可以从上传走完整个入库、搜索、选择、分析、预览和下载流程。

### P3：PDF 报告与谱系版图

- 统一 PDF 版式与中文字体；
- PDF 在线预览与下载；
- 论文关系边计算和解释；
- 教师/论文/主题的邻域图；
- 时间演化和企业方案证据子图；
- 数千篇规模下的按需加载与性能测试。

**完成标准**：点击任意关系边可说明关系类型、强度组成和证据；报告的 MD 与 PDF 内容一致。

### P4：工程化和部署

- 用户与角色权限；
- 企业数据和院校数据隔离；
- 后台任务队列、取消和重试；
- 数据备份、迁移和审计；
- CI、部署、安全扫描和运行监控；
- 多用户并发与公网部署评估。

## 11. 暂时不要抢跑的功能

- 不先做看起来很满的“2921 篇全量大图”；
- 不先做模型微调，当前数据规模和任务更适合 RAG；
- 不先引入图数据库和复杂微服务；
- 不先做浏览器内完整 draw.io 编辑器；
- 不把 OCR、视觉模型、专利库、法规库混入第一个企业端迭代；
- 不先做公网多租户，避免在权限和版权边界未完成前扩大风险。

这些能力不是不要，而是应在核心闭环有真实使用反馈后再投入。

## 12. 产品验收原则

后续每个版本都应满足以下底线：

1. 企业需求的结构化字段能回到原文；
2. 方案中的技术事实能回到论文页码或明确标为推断；
3. 每个技术模块有输入、输出、依赖和验收标准；
4. 匹配分与转化就绪度分开；
5. 转化评估同时显示证据完整度和未知项；
6. 用户可以修改拆解、方案和路线，修改记录可追踪；
7. 未经明确同意，不把本地论文片段发送到外部 API；
8. MD、PDF 和网页预览来自同一份结构化报告；
9. draw.io 文件是可编辑源文件，不只是改后缀的图片；
10. 谱系图中的每条关系可以解释，不用视觉距离冒充事实；
11. 真实论文、企业数据和 API Key 不进入公开 Git 仓库；
12. 新功能有离线测试、失败提示和可恢复路径。

## 13. 需要在真实使用中确认的产品问题

这些问题不阻塞开始 P0/P1，但会影响后续细节：

- 企业端最终报告主要给技术负责人、管理层还是成果转化部门；
- 企业通常能提供哪些定量目标、预算、周期和现有工艺数据；
- 论文库预计是一位教师、一个学院还是全校规模；
- 上传论文是否都具备本地保存和外部 API 处理授权；
- 是否需要多人审核、批注和方案版本对比；
- 转化评估的行业权重是否需要按领域配置；
- PDF 报告是否需要学校/企业 Logo、固定模板和签章页；
- 谱系关系是否需要接入参考文献、专利或项目数据。

在没有真实数据前，这些字段保持“可配置、待确认”，不写死成产品事实。

## 14. 下一步建议

下一轮开发直接进入 **P0 + P1 的第一小步**：

1. 先定义企业需求模块、候选方案、路线节点、评估结果和证据声明的 JSON 数据契约；
2. 将当前企业需求结果页改成“需求确认 → 方案生成”的分步工作台；
3. 先用现有一位教师、三篇论文跑通一个真实可追溯方案，不追求大规模界面；
4. 验证模块级检索和报告结构后，再接入论文上传库与院校端三栏页面。

这样能够最早验证真正重要的问题：系统是否能把企业需求可靠地翻译成一条有论文证据、能被工程人员审阅的技术路线，而不是只把现有匹配结果换一个更漂亮的界面。
